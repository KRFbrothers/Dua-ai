# Home widget and Android share targets

Long-press the launcher → Widgets → **Dua AI toolbar**. The resizable 4×2 toolbar has an Ask Dua AI area, dictation and Live voice buttons, plus Camera, Photos, Files and Screenshare / Video shortcuts. All seven immutable Activity pending intents have distinct widget/action identities. The widget itself never reads account/chat data, records audio, runs a service or calls an API. System light/dark resources supply its palette; the voice button stays purple.

Widget actions open the same single MainActivity. Ask focuses the active chat composer; camera/photo/file shortcuts reuse existing picker handlers; the mic opens dictation and Live opens the existing live-voice screen. Microphone permissions and owner/backend session checks remain in those screens. Opening a shortcut never sends a chat message automatically. Screenshare / Video opens a clearly labelled Coming soon page: screen capture/video chat is not implemented in the current engine, and no MediaProjection session is simulated.

Android's share sheet offers **Dua AI** for plain text, CSV, images, audio, video, PDF, DOCX and XLSX, and **Remember this** for plain text only. Text is appended to an existing draft; it does not replace it or send automatically. Content URIs from EXTRA_STREAM/ClipData are deduplicated and passed to the existing attachment pipeline. Only three files are selected per share. Incoming file shares wait with a visible notice until the current attachments/uploads are sent or removed; metadata preparation is reserved synchronously so queued shares cannot replace an earlier selection. Oversized text is limited to 32000 characters with a notice; private file paths and the app's own camera-provider URIs are rejected. Existing file-size/type/provider restrictions remain enforced. Advertising a share MIME does not add backend codecs: DOCX/video and unsupported provider/type combinations show the existing clear attachment error rather than claiming a successful upload or response. URI grants can expire after process death; share again if the source app cannot grant persistent access.

Entry requests wait behind onboarding, account screens and busy reply/data/live-session actions. Login or Skip remains explicit. A saved-state queue survives recreation and removes an entry before dispatching its picker, preventing repeat launches. A full queue rejects the new entry with a toast instead of losing an older request. Existing notification/project shortcut routing is retained.

**Remember this** opens a full-page editable confirmation, with the current account shown. It does not silently create a memory or enable Memory. Save requires a signed-in account, matching owner, a readable cache and no conflicting operation. The existing 10-note / 200-character limits and deduplication apply. The success toast says the memory is cached and needs sync; the existing server-first sync protocol remains authoritative. No new account/storage API or authentication bypass is introduced.

The six supplied 960×960 vector paths are stored as Android vector resources and reused by the widget, Remember target/confirmation, composer and voice controls. Local JVM/Compose tests cover intake, saved-state consumption, widget button intents/touch targets, manifest MIME registration, draft preservation/focus, onboarding, memory confirmation and ownership. Physical launcher resize, external app URI grants, real camera, microphone and live-backend sessions still need device verification.
