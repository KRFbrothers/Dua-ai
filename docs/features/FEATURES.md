# Dua features: current state and remaining work

Updated 11 October 2026. Dua is an Android app (`app/`) backed by a server-side API in `web/` deployed on Google Cloud Run (`dua-api`). The old browser client (pages, browser storage, browser speech/camera previews and the `/preview/` design sandbox) was removed; `dua-api` now also serves the separate owner-only website in `website/` (see [WEBSITE.md](../WEBSITE.md)). This document describes the Android app and the backend. "Prepared" means implemented in source but dependent on server configuration that this repository cannot verify. See [ROADMAP.md](../ROADMAP.md) for phase planning.

## Chat history (server-first)

Chats and memory notes are authoritative on the server (the signed-in account's cloud snapshot). The Android app keeps only a disposable cache in app-private SharedPreferences for offline viewing and fast startup: when online the app hydrates from the server and the server copy wins over the cache; when offline it falls back to the cache. Messages, draft and selected model are retained; Home supports title/preview search, reopening and confirmed deletion. Clearing app storage removes only the cache and the next sync restores it from the server. Android backup and device transfer exclude cached chat history, account sessions and automatic-sync consent; other preferences may be backed up according to device settings; see [PRIVACY.md](../PRIVACY.md).

## Attachments and photos

**Stored files (signed-in owner):** Photos, Files and the Audio tile (record a voice note or pick audio) upload straight to the private `dua-files` Supabase bucket with progress and cancel, up to 50 MB each and 10 per message. Messages keep references and show tappable file chips that open a 10-minute signed link. The backend re-attaches files by storage path on follow-ups, parses spreadsheets to CSV, extracts PDF text for providers without PDF input, and transcribes audio before answering (the transcript is saved with the message). Removing a cached chat keeps saved server files. Per-file cleanup retains paths referenced in the server snapshot; discarded unsent uploads have separate cleanup. Data controls shows storage used and offers the reviewed Delete all uploaded files action, which permanently removes files even when chats reference them. Signed out, the + sheet explains that sign-in is needed for large files and the inline path below keeps working.

The inline path sends at most 3 files / 2 MiB total with the current message; each text/code file is limited to 256 KiB. The backend validates contents and adds inline image/PDF or decoded text parts only to the final user message. Successful replies clear the selection; Stop/errors retain it. History stores filenames and replies without file bytes; pending bytes are held only in memory. For a signed-in owner, decoded text and stored-file metadata needed for follow-ups are retained in the server snapshot; raw file bytes remain in private Storage.

Camera capture is delegated to the device camera app through `TakePicture` and a restricted FileProvider cache path, so no CAMERA permission is needed. A cancelled/failed capture keeps the previous selection. Capture files are removed after reading, on failure/cancel or when launch fails; files abandoned by process death are pruned after 24 hours when capture next starts.

When a selection exceeds 2 MiB, PDF/TXT bytes are reserved and the remaining capacity is shared across selected JPEG/PNG/WebP images. Oversized images are resized to at most 2048 pixels on the longest side, with lower dimension/quality attempts until each fits; nothing is upscaled. Sources are bounded to 10 MiB and to 16000 pixels per side / 40 million pixels, decoding is sampled to bound bitmap memory, EXIF rotation is applied, transparency is flattened on white, and output is a metadata-free JPEG named `-resized.jpg`. Selections that cannot fit leave the previous selection intact.

## Voice

- **Voice input to draft:** Android `SpeechRecognizer` with a user-initiated start, `RECORD_AUDIO` permission (denial links to app Settings), service-availability checks and a 30-second timeout. A completed transcript is reviewed/edited and appended to the existing draft; sending remains a separate action. No raw audio is stored by the app, but the selected device speech service may process audio remotely.
- **Read aloud:** explicit Read aloud / Stop on completed replies using Android `TextToSpeech`. Long replies are split into chunks of at most 300 code points; a stalled chunk times out after 45 seconds. Playback requests transient audio focus and stops on focus loss, backgrounding, navigation or a new prompt.
- **Foreground hands-free:** an explicit Start for a separate conversation. Final speech sends automatically, the reply is read with device TTS, then the next turn listens. Stop/Back/background cancels recognition, the pending request and playback; returning to the foreground never auto-starts. Errors stop the loop. This is device speech recognition plus a text chat reply plus TTS, not simultaneous listening/speaking.
- **Optional generated reply voice:** uses the authenticated, owner-restricted `/api/voice/audio` endpoint with a Grok, Gemini or ElevenLabs voice chosen in Settings › Voice (see [PROVIDERS.md](../PROVIDERS.md)). Device speech remains the default; only tapping a completed reply sends its text. Audio is bounded, kept in memory and released on Stop/navigation/background/offline/account changes. Hands-free still uses device speech.
- **Live voice (signed-in owner):** a full-screen realtime conversation with xAI (server-minted short-lived token, live captions, interrupt by talking, mute/end, microphone foreground service, durable daily minute cap); the transcript is saved to the chat. `DUA_VOICE_REALTIME=0` falls back to hands-free. See [PROVIDERS.md](../PROVIDERS.md) and [PRIVACY.md](../PRIVACY.md).

## Local data controls

Data controls export the cached view of server-backed chats and unsent drafts as a version-1 `dua-chat-export` JSON envelope through the system CreateDocument picker. Backups preserve extracted attachment text, stored-file references/audio transcripts, code runs/outputs, Build repositories/file lists/proposals/PR links, summaries and Imagine state; Project definitions, custom instructions, tasks, project memory notes/switches and chat project references are included; raw file/audio bytes, account session tokens and global memory notes are not included. Stored media references are included; provider-only temporary video URLs are not. Import uses OpenDocument, shows the chat count for confirmation and creates fresh chat/message IDs, remapping summary references to the copied messages. Imported chats initially belong to the phone cache and become server-backed after authenticated sync; original Storage objects still require owner sign-in and must exist. Existing chats, the active draft and pending attachments are kept. Backups and the combined imported cache are limited to 4 MiB, 100 chats, 500 messages per chat, 8,000 UTF-16 code units per draft and 1,048,576 per message. Malformed or lossy metadata is rejected entirely. Export validates the complete backup before opening its destination; import validates the combined cache before writing it. Clear cached chats requires confirmation, cancels pending replies, persists empty history before updating the UI and attempts camera-cache cleanup. Storage failures are reported rather than shown as success.

## Settings, notifications, memory and sharing

- **Appearance:** Dark, Light and System themes; Default, System, Serif and Monospace fonts; and a haptic preference, persisted in `dua_preferences`.
- **Permissions:** native microphone permission links to app Settings; camera/files are delegated to camera/photo/document apps. Status refreshes when returning from Settings.
- **Reply notifications:** explicit opt-in and permission, generic content without chat text, a test action and a conversation tap destination. Only replies that complete while the process is alive can notify; there is no server push.
- **Personal memory:** off by default, at most ten notes of 200 UTF-16 code units each, with inspect/edit/delete and confirmed delete-all. The device switch enables Personal notes read from the server for project-aware chat, as untrusted preference context; Coding, Business and custom projects omit global memory. Remember-statement proposals require per-note approval.
- **Sharing:** review and share/copy completed messages as plain text. Unsent drafts, stopped/pending replies, file bytes and audio are excluded. No public hosted link is created.

## Accounts and cloud sync

See [SUPABASE.md](../../SUPABASE.md). The app signs in with native Google sign-in (`/api/account/google-token`) from the first-launch welcome screen or Settings → Profile, or with owner-only email login under Account, and supports greetings with the Google account name, device logout (Profile only), optional account deletion, and explicit cloud review/upload/download/clear through the backend's `/api/account/*` and `/api/cloud` endpoints. Tokens are encrypted with Android Keystore and excluded from backup/device transfer.

Foreground automatic cloud sync requires explicit device/account consent and uses foreground/online synchronization, local-change debounce, remote polling and bounded retry. Backgrounding, logout, account switches, pending replies and manual data/account operations stop or pause pending work. Deletions, competing edits, revision conflicts and invalid storage pause for review. Background services and realtime collaborative editing remain future work.

## Providers, web sources and integrations

Gemini (Dua/Gemini), ChatGPT, Claude, Grok and Kimi are routed by the backend. All accept validated UTF-8 TXT attachments; explicit server MIME settings enable model-supported images and, for ChatGPT/Claude, PDFs. The app checks the published formats before sending and keeps unsupported selections and drafts. See [PROVIDERS.md](../PROVIDERS.md).

Chat has session-only Web: Off/Search/Read link modes, Off by default. Search uses the provider's native search for Gemini, ChatGPT and Grok (Google Search grounding, OpenAI and xAI `web_search`) with structured citations shown as source chips (favicon, title, domain); Claude and Kimi, the `DUA_SEARCH_PREFER_BRAVE` flag and the fallback run one Brave query and supply bounded result snippets. Grok adds an X toggle (`x_search`, off by default, about $5 per 1,000 posts). Long chats are no longer cut at 39 messages: each provider has a context budget, older turns are summarised by the current provider, the summary is cached with the chat and extended incrementally, and the chat shows an "Earlier messages summarised" divider; Read link reads one public HTTPS text page with DNS pinning, redirect checks and size/time limits. Replies carry a Sources footer with safe clickable HTTPS links that persists through copy, history, sharing and cloud snapshots.

**Run code (Phase 5).** The composer's Run code chip (shown when `/api/config.code` exists) adds the provider's hosted code tool to the next replies: Gemini `code_execution` for Dua/Gemini (on by default when Gemini is configured, no extra charge, Python only, 30 s per run); OpenAI and xAI `code_interpreter` only when `OPENAI_CODE_EXECUTION=1` / `GROK_CODE_EXECUTION=1` because both bill per container or call. Nothing runs on the phone or on the Node API server. Stored spreadsheets reach the model as CSV text (first 300 rows per sheet by default) and text files as text, so the code works on that content. Streamed replies carry `code` events (code, then output and outcome); the app shows each run as a collapsed "Ran code" block above the answer (monospace, copy code/output, "Code failed" / "Code timed out"), and Copy response includes them. Runs are saved with the reply in the server snapshot and phone cache; exports remain user-initiated. Retry keeps the original Run code choice. A model that rejects the tool answers again without it, with a note.

**Build mode (Phase 5B, read-only).** The composer's Build chip opens a sheet listing the owner's repositories; picking one ties the chat to it (saved with the chat in the server snapshot and phone cache) and shows "Build · repo" as the first chip. Each Build message goes to `/api/chat` with `mode: "build"` and the repository; the server checks setup, the signed-in owner and the repository, then lets Gemini call `list_files`, `read_file` and `search_code` (GitHub GET requests only) for up to 6 rounds, at most 40 files and 600 KB per reply, and forces a final answer before the chat deadline. Answers propose changes as ```diff blocks, which the app colours (added green, removed red, hunks blue). Above the answer, "Read N files · repo" chips show what was read (tap to open on GitHub; long lists collapse to four plus "+N more"). The file list is kept in the server snapshot and phone cache. Build mode works with Dua and Gemini; turning on Reasoning, Search, Run code or Imagine leaves Build. If the server, sign-in or Gemini is not ready, the sheet says what is missing instead of hiding the mode.

**Pull requests (Phase 5C, approved by the owner).** When `DUA_BUILD_PR=1` and a separate write token are set, the model can call `propose_changes`. That call only returns a proposal to the app: a review card shows the title, summary and every file (added, changed or deleted) with a coloured diff. Nothing is written until you tap **Create PR** and confirm the dialog (the title can be edited there). The server then checks the proposal again (paths, sizes, and that no file changed since Dua read it), creates a new `dua/…` branch and a commit with the Git Data API, and opens a draft pull request. The card becomes a link to the pull request; errors are shown in plain text. The proposal and pull request link are retained in the server snapshot and disposable phone cache. Dua never merges, force-pushes or deletes branches. Running commands is still not implemented (see ROADMAP.md).

The read-only GitHub connector (`/api/connectors/github`) lists repositories, reads the file tree and files, and searches code for the signed-in owner when a token, owner email and feature flag are configured. `/api/setup` reports which integration groups are configured without exposing credentials.

## Validation status

The default Android JVM/Compose suite runs in CI with `bash ./gradlew :app:testDebugUnitTest -Pdua.ui-record --no-daemon --max-workers=2` from the repository root. It covers history, import/export, attachments/photo policy, camera store, accounts, cloud sync, voice sessions, network transport, integration capabilities and current UI fixtures using mocked services or local TLS servers. The UI flag records those fixtures; historical classes under `app/src/test/java/com/dua/ai/screenshots/` remain excluded unless `-Pdua.screenshots` is supplied. The backend CI command is `npm run test:ci` from `web/`, with mocked providers/storage and a JUnit report. After installing dependencies, the separate Imagine smoke script is `node scripts/imagine-smoke.mjs` from `web/`; it is not part of routine CI. [README.md](../../README.md#android-and-routine-checks) lists the commands, prerequisites and artifact paths grounded in the Gradle configuration, npm scripts and workflow. No live provider, storage, search or audio request is part of routine checks; physical-device behavior (speech, audio focus, camera/pickers, notifications, Keystore, lifecycle) and live deployment checks remain to be verified using [RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md).

## Projects and instructions

**Full-message history search** is implemented in source: current-project cached user/assistant text, drafts and saved Run code/code output; one result per chat with highlighted context, date groups and open/clear controls. Search runs on a background dispatcher after a short debounce, makes no provider request and discards stale query/project/snapshot results. Server-wide/semantic search and direct jumps to matching turns remain pending. See [HISTORY_SEARCH.md](HISTORY_SEARCH.md); device/live sync-refresh checks remain pending.

Implemented in source: Personal/Coding/Business defaults, create/edit/archive, project-scoped history, persisted chat project IDs, custom instructions from the owner server snapshot, cloud sync and project-aware JSON import/export. Old chats default to Personal. Divergent edits to the same project pause automatic sync; reviewed download uses server settings and keeps phone-only projects. Imports copy differing project settings rather than overwrite current instructions. Coding, Business and custom projects have editable, server-resolved memory with separate on/off switches; Personal keeps its existing editor. See [PROJECT_MEMORY.md](PROJECT_MEMORY.md). Dedicated project file libraries and configured tools per project remain pending. Live voice uses Personal without custom instructions; other projects use hands-free Voice mode for scoped chat requests. See [PROJECTS.md](PROJECTS.md). Physical-device and live provider verification of Projects is pending.


## Project tasks

Implemented in source: project to-do lists, add/edit titles, complete/reopen, confirmed delete, archived read-only lists, owner snapshot sync and task-only JSON backup/import. Limits: 100 tasks per project and 200 UTF-16 code units per title. Project edits/reset keep tasks, divergent project edits pause sync, and task titles are not automatically included in AI prompts. Tasks require the updated backend/APK. Optional due dates and opt-in device reminder notifications are implemented ([REMINDERS.md](REMINDERS.md)). **Projects → Daily planner** adds local-day deadline groups, earlier unfinished tasks, the undated inbox, project filters, date navigation and completion/reopen controls from the same snapshot ([PLANNER.md](PLANNER.md)). Recurring tasks, separate planned dates and calendar integration remain pending. See [TASKS.md](TASKS.md); physical-device/live sync verification is pending.
